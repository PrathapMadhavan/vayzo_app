1. Purpose
This document is the database implementation contract for VAYZO Phase 1. It is written so a developer using Cursor or Codex can create the Laravel migrations, models, relationships, indexes, seeders and API persistence layer without inventing the core schema.
Do not change table names, enum meanings, primary relationship rules or request lifecycle states without Technical Lead approval.


2. Phase 1 Business Scope


Food Delivery


Buy &amp; Get It — customer can request items from one or multiple local shops; a partner purchases and delivers them.


Local Bike Ride Booking


Local Car Booking


Customer text request and voice-to-text request.


Customer wallet/payment and partner earnings.


Super Admin operations, pricing, service areas, support and reporting.
Out of scope: bus/train ticket booking, recharge, bill payment, flight/hotel booking and a large catalogue-first grocery marketplace.


3. Database Design Principles


Use InnoDB and utf8mb4 for all application tables.


Use BIGINT UNSIGNED AUTO_INCREMENT primary keys for internal IDs unless a table is explicitly a lookup/config table.


Use UUID/ULID public identifiers where API exposure is required; never expose sequential internal IDs as the public request/order reference.


All business tables should have created_at and updated_at. Use deleted_at only where soft deletion is explicitly useful.


Store money as DECIMAL(12,2), never FLOAT or DOUBLE.


Store latitude/longitude as DECIMAL(10,7).


Store timestamps in UTC at the database/application layer and convert to the user's local timezone for display.


Use foreign keys for core relational integrity.


Use status-history tables for important state transitions; do not rely only on the current status column.


Do not store raw payment card details.


Store uploaded files as storage keys/URLs and metadata, not binary files in MySQL.


Never store a customer's raw password if OTP-only authentication is used.

5. High-Level ER Model
Core relationship:
users → customer_profiles / partner_profiles → requests → request_pickups / request_items / request_status_history → assignments → partner → payments / earnings
Food relationship:
restaurants → restaurant_categories → restaurant_products → food_orders → food_order_items
Ride relationship:
requests → rides → ride_locations
Finance relationship:
users → wallets → wallet_transactions; requests → payments; partners → partner_earnings → partner_payouts
Support relationship:
users → support_tickets → support_messages

21. Foreign Key Rules


Core ownership relationships should use ON DELETE CASCADE only when child data has no independent business value.


Financial, payment, request and audit history must not be physically deleted through cascade.


Prefer RESTRICT/NO ACTION for financial and operational history.


Use SET NULL for optional admin/user references such as verified_by or processed_by when the admin account can be deactivated.


Soft-delete master records such as restaurants, products and addresses where historical records must remain readable.

27. API / DB Security Rules


Never trust client-provided customer_id or partner_id; derive identity from authenticated token.


Verify that a partner is eligible for the requested service before assignment.


Verify ownership before a customer can view/update a request.


Verify assignment before a partner can update a request.


Admin-only operations must be protected by role/permission middleware.


Validate all uploaded bill/document files.


Do not expose internal database IDs where a public ULID is available.


Use idempotency keys for payment creation and other retry-sensitive operations.


Keep payment gateway webhook handling idempotent.
